# Diagrams

`work-lifecycle.lifecycle.json` is the `WorkState` machine as
`wirk_core::fold` actually writes it: every state is one the fold
assigns, and every transition is one it makes. It is authored source,
not generated from the code, so it goes stale the way any document does
— when `fold` changes, change this too.

It renders with Archify's `lifecycle` renderer, a reference tool on the
development box, not a dependency of this product:

```sh
node refs/archify/archify/bin/archify.mjs \
  render lifecycle docs/diagrams/work-lifecycle.lifecycle.json out.html
```

Nothing in `wirk` reads or ships this. The rendered HTML is ~710KB and
is deliberately not committed; regenerate it when you want to look at
it.

## Why this renderer, and why only here

Its state vocabulary — `start`, `active`, `waiting`, `decision`,
`success`, `failure`, `neutral` — maps one-to-one onto `WorkState` with
nothing coerced, and its layout validator catches real errors: it
refused three genuine edge-through-node overlaps in the first draft of
this file.

It is not used in `wirk browser`. That page re-reads wirkd on every
request and ships inside a single Rust binary; this renderer turns
authored JSON into a static document and needs a Node runtime to do it.
For one live page that is a large new dependency for no gain. For an
authored document regenerated by hand when the state machine changes,
it costs nothing at runtime and does the job well.

## One thing the fold does not do

`WorkState::Blocked` exists in the enum and `fold` never assigns it.
Nothing here draws it, because nothing reaches it.
